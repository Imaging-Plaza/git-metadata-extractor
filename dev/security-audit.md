## CRITICAL (1)

### Unauthenticated /query ad-hoc SQL allows arbitrary local file read (LFI) and FS enumeration via DuckDB built-ins
- **id:** `query-adhoc-lfi-duckdb` · **kind:** vulnerability · **confidence:** high · **group:** standalone-index-apps
- **endpoint:** POST /query (sql=...) on all 6 apps
- **location:** `src/index/github_repos/retrieval/sql.py (and identical openalex/orcid/renkulab/swissubase/zenodo_records retrieval/sql.py):27`
- **what:** _validate_adhoc only checks that the trimmed query starts with SELECT/WITH and that it does not contain a word-boundary match for a fixed keyword blocklist (attach, copy, pragma, install, load, export, import, create, drop, alter, insert, update, delete, truncate). The query then executes on store.connect(), which opens DuckDB in READ-WRITE mode (src/index/openalex/storage/duckdb_store.py:49 `duckdb.connect(str(self.db_path))` with no read_only=True; the read_only() context manager exists but is NOT used by _execute). DuckDB ships built-in table functions read_text(), read_blob(), read_csv(), and glob() that read arbitrary filesystem paths and require NO install/load (so the blocklist never triggers) and start with SELECT. I confirmed against duckdb 1.5.3: `SELECT content FROM read_blob('/tmp/secret.txt')` returned the file bytes, `SELECT * FROM read_csv('/tmp/secret.txt', header=false, columns={'l':'VARCHAR'})` returned the file contents, and `SELECT * FROM glob('/tmp/*')` enumerated the directory. An unauthenticated attacker can therefore read /app/.env (API_TOKEN, GME_GITHUB_TOKEN, RCP_TOKEN), /proc/self/environ, SSH keys, etc., and enumerate the container filesystem. The 'read-only SQL surface' docstring is false: the connection is writable and the guard is a bypassable string blocklist, not a parser/read-only enforcement.
- **repro/trigger:** POST /query {"sql":"SELECT content FROM read_blob('/app/.env')"} -> returns the .env contents base64/blob; POST /query {"sql":"SELECT * FROM glob('/app/**')"} -> lists files. Verified the DuckDB functions and the read-write connect() in code.
- **fix:** Execute ad-hoc queries on a genuinely read-only connection (use the existing read_only() context manager: duckdb.connect(path, read_only=True)) AND disable filesystem/extension access on that connection via config, e.g. duckdb.connect(path, read_only=True, config={'enable_external_access': False}) (DuckDB's enable_external_access=false blocks read_csv/read_blob/read_text/glob/attach/copy/install/load). Do not rely on a keyword regex. Ideally also disallow ad-hoc SQL entirely on an unauthenticated app and expose only predefined queries.
- **verifier:** Confirmed against the actual code and empirically reproduced on duckdb 1.5.3 (the exact version cited).

Code verification:
- src/index/github_repos/api.py:77-91 — POST /query has NO auth (no Depends/Security, no middleware, no API key). It calls run_adhoc(req.sql, req.params) with attacker-controlled SQL straight from the request body. Grep across all index api.py files returns zero HTTPBearer/api_key/Depends/verify references. The app is served via the CLI `serve` command (cli.py:188-196) with uvicorn binding host default 0.0.0.0, port 8004 — network-exposed, unauthenticated.
- retrieval/sql.py:27-34 — _validate_adhoc only checks the trimmed query starts with select/with and matches a fixed word-boundary keyword blocklist (attach, copy, pragma, install, load, export, import, create, drop, alter, insert, update, delete, truncate). read_blob/read_csv/read_text/glob are NOT in the blocklist and start with SELECT, so they pass validation.
- retrieval/sql.py:99 — _execute runs `store.connect().execute(sql, ...)`. connect() (storage/duckdb_store.py:47-51) is `duckdb.connect(str(self.db_path))` with NO read_only=True. The read_only() context manager (lines 61-67) exists but has zero usages in the retrieval/serving path (grep confirms only the connect() call at sql.py:99 in retrieval). So the docstring's "read-only SQL surface" claim is false: the connection is writable and external file access is enabled.

Empirical reproduction (duckdb 1.5.3): SELECT content FROM read_blob('/tmp/secret.txt') returned the file bytes; read_csv and read_text returned file contents; SELECT * FROM glob('/tmp/*') enumerated the directory — all passed the exact validator logic. I also verified the remediation claims: read_only=True ALONE does NOT block read_blob (LFI still works), whereas config={'enable_external_access': False} raises PermissionException and blocks it. So the proposed fix is technically correct, and read-only alone would be insufficient.

Scope: identical vulnerable code in all 6 cited apps (github_repos, openalex, orcid, renkulab, swissubase, zenodo_records) — grep for @app.post("/query") confirms exactly these 6. Note the github_repos store has no enable_external_access config; only epfl_graph uses read_only=True with a (still-empty) config dict, and epfl_graph is not in the vulnerable set.

Impact: an unauthenticated attacker who can reach any of these apps can read arbitrary local files (/app/.env containing API_TOKEN, GME_GITHUB_TOKEN, RCP_TOKEN; /proc/self/environ; SSH keys) and enumerate the filesystem. This is a textbook unauthenticated LFI / secret-exfiltration primitive.

Severity: Critical is appropriate. One caveat affecting exploitability in this specific repo: the production tools/deploy/docker-compose.yml deploys only the main gme-api (gunicorn :1234), not these 6 standalone index apps, so their public exposure depends on operational deployment not captured in-repo. But the apps are designed to be served (serve CLI binds 0.0.0.0) and the code unconditionally implements the unauthenticated attacker-controlled writable-DuckDB SQL surface. The vulnerability is genuinely present and exploitable wherever any of these apps is reachable; keeping Critical.


## HIGH (7)

### All v1 extraction and cache-management endpoints are unauthenticated while v2 requires a bearer token
- **id:** `v1-cache-no-auth` · **kind:** vulnerability · **confidence:** high · **group:** v1-and-cache
- **endpoint:** GET /v1/*, /v1/cache/*
- **location:** `src/api.py:784`
- **what:** Every v1 route (org/user/repository extraction) and EVERY cache-management route (stats, entries, cleanup, clear, enable, disable, invalidate) is declared on the bare `app` with no `Depends(verify_token)` and no app/router-level dependency. The only dependency on the extraction routes is `Depends(validate_github_token)` (src/api.py:802,923,1093,1279,1450), which merely confirms the SERVER's own GME_GITHUB_TOKEN works against GitHub's rate_limit API (src/v1/utils/github_dependency.py:17-118) — it authenticates nothing about the caller. By contrast, the v2 router applies `Depends(verify_token)` (src/v2/auth.py, enforced on ~50 v2 routes in src/v2/api.py) which validates a bearer token against API_TOKEN. The production stack (tools/deploy/docker-compose.yml:35-36) publishes gme-api directly on host port 1234 with no auth proxy in front, so any network client can drive the expensive LLM/GIMIE pipelines and read/mutate cache state unauthenticated.
- **repro/trigger:** With API_TOKEN set in prod, run `curl -X POST http://host:1234/v1/cache/clear` (no Authorization header) -> 200 and the entire cache DB is wiped. Same for `curl http://host:1234/v1/repository/llm/json/github.com/owner/repo` which triggers a full LLM pipeline with no token.
- **fix:** Add `_token: Annotated[str, Depends(verify_token)]` (from src.v2.auth) to all five v1 extraction routes and all seven cache routes, or attach `dependencies=[Depends(verify_token)]` to the relevant route group. Keep `validate_github_token` as the server-token check but stop treating it as caller auth.
- **verifier:** Confirmed against the actual code. The 5 v1 extraction routes (src/api.py:784,901,1031,1198,1425) are declared on the bare `app` and carry only `Depends(validate_github_token)` (lines 802,923,1093,1279,1450). That dependency (src/v1/utils/github_dependency.py:17-118) reads the SERVER's own `GME_GITHUB_TOKEN` env var and validates it against GitHub's /rate_limit endpoint; it never reads the incoming request's Authorization header, so it authenticates the deployment, not the caller. The 7 cache-management routes (stats:1542, entries:1562, cleanup:1615, clear:1633, enable:1651, disable:1667, invalidate:1685) have NO dependency at all — not even validate_github_token. The FastAPI() constructor at line 183 has no `dependencies=` kwarg, and grep over api.py module scope shows zero references to verify_token / API_TOKEN / HTTPBearer / Authorization; the only @app.middleware (line 369) is request-ID logging that calls call_next unconditionally. By contrast, src/v2/auth.py verify_token validates a bearer token against API_TOKEN via hmac.compare_digest (failing closed with 503 if unset) and is wired into ~50 v2 routes via Depends(verify_token) (grep shows ~40+ occurrences in src/v2/api.py). The deployment (tools/deploy/docker-compose.yml:35-36) publishes gme-api on host port 1234 with no auth proxy. So `curl -X POST http://host:1234/v1/cache/clear` reaches clear_all_cache() -> cache_manager.clear_all_cache() with no auth (cache wipe / DoS), and the v1 LLM/GIMIE extraction routes can be driven unauthenticated to burn LLM tokens and external API quota. Real authorization gap and an inconsistency vs the deliberately-authenticated v2 surface. High is the correct severity: it is unauthenticated state mutation + cost/DoS abuse, though not RCE or data-exfiltration of secrets, so not critical. The proposed fix (add Depends(verify_token) to the 5 extraction routes and 7 cache routes, or a router/app-level dependency) is appropriate.

### Unauthenticated POST /v1/cache/clear destroys the entire cache (DoS / cost amplification)
- **id:** `cache-clear-destructive-no-auth` · **kind:** vulnerability · **confidence:** high · **group:** v1-and-cache
- **endpoint:** POST /v1/cache/clear
- **location:** `src/api.py:1633`
- **what:** clear_all_cache() runs `DELETE FROM cache_entries` (src/v1/cache/cache.py:442-455) with no auth and no confirmation. Because LLM/GIMIE results carry TTLs of up to 365 days and are very expensive to regenerate, an unauthenticated attacker who repeatedly POSTs to /v1/cache/clear forces every subsequent extraction to re-hit the paid LLM provider and GitHub API, amplifying cost and latency and potentially exhausting the GitHub rate-limit pool. /v1/cache/cleanup and /v1/cache/invalidate/{api_type} share the same exposure.
- **repro/trigger:** curl -X POST http://host:1234/v1/cache/clear -> {"message": "Cleared N cache entries"}; loop it to keep the cache empty.
- **fix:** Require verify_token on the mutation endpoints (clear/cleanup/enable/disable/invalidate). Consider also gating /v1/cache/clear behind an explicit confirm flag and audit-logging the caller.
- **verifier:** CONFIRMED real and exploitable on the deployed stack.

Auth gap verified:
- src/api.py:1633 `clear_all_cache()` and the sibling mutation endpoints `/v1/cache/cleanup` (1615), `/v1/cache/enable` (1651), `/v1/cache/disable` (1667), `/v1/cache/invalidate/{api_type}` (1685) declare NO FastAPI dependency at all — no `verify_token`, no `validate_github_token`, no `dependencies=` on the app constructor (src/api.py:183-235), and the only `@app.middleware("http")` (src/api.py:369) is a request-context/logging shim that performs zero authentication.
- This is a real inconsistency, not a deployment assumption: the v1 extraction endpoints DO gate on `Depends(validate_github_token)` (src/api.py:802, 923, 1093, 1279, 1450) and every v2 endpoint gates on `Depends(verify_token)` (src/v2/api.py, ~50 call sites). The cache endpoints are the unprotected outliers, and the proposed fix (`verify_token` from src/v2/auth.py) already exists.

Destructive behavior verified: clear_all_cache() -> cache_manager.clear_all_cache() (src/v1/cache/cache_manager.py:286-288) -> APICache.clear_all() which executes `DELETE FROM cache_entries` (src/v1/cache/cache.py:450). It wipes all entries, active and expired, irreversibly.

Reachability/repro verified against the deploy branch: the deployed entrypoint is `gunicorn src.api:app` (tools/image/Dockerfile:53) bound to 0.0.0.0:1234 (tools/config/gunicorn_conf.py:13), and the new tools/deploy/docker-compose.yml:35-36 publishes it to host `${APP_PORT:-1234}:1234` with no auth proxy in the stack. The v1 `app` is the served application (it even `include_router(v2_router)` at src/api.py:365). So the finding's repro `curl -X POST http://host:1234/v1/cache/clear` is accurate and would return `{"message": "Cleared N cache entries"}`. Looping it keeps the cache empty, forcing every extraction to re-hit the paid LLM provider and the GitHub API (consuming the GME_GITHUB_TOKEN rate-limit pool) — genuine cost/latency amplification and rate-limit exhaustion.

One factual inaccuracy in the writeup: it claims TTLs "up to 365 days." The v1 cache config (src/v1/cache/cache_manager.py:19-29) caps at DEFAULT_TTL_DAYS=30 with overrides llm=30, orcid=14, github_user/org=7, gimie=1 — there is no 365-day TTL in this code path. This overstates the regeneration value but does not negate the issue (LLM/GIMIE/GitHub results are still expensive to regenerate).

Severity kept at high: trivially exploitable, destructive, internet-exposed by the deploy compose, and a clear auth-consistency gap with an off-the-shelf fix. Blast radius is bounded though — it is a cache (no primary-data loss), data regenerates automatically, and the 30-day-max TTL plus the TTL exaggeration mean real-world cost impact is less than the writeup implies, so this sits at the lower end of high / borderline medium.

### v1 extraction endpoints have no rate limiting; unauthenticated callers can exhaust LLM budget and GitHub tokens
- **id:** `v1-no-rate-limit-llm-dos` · **kind:** vulnerability · **confidence:** high · **group:** v1-and-cache
- **endpoint:** GET /v1/{org,user,repository}/...
- **location:** `src/api.py:784`
- **what:** None of the v1 extraction routes apply any per-client throttling (no slowapi/Limiter anywhere in src/api.py or src/v2/api.py for inbound requests). Each call kicks off a heavyweight pipeline: multiple GitHub REST/GraphQL calls, web/Infoscience/ROR lookups, GIMIE extraction, and multi-stage paid LLM agent runs. force_refresh=true bypasses the cache entirely. Because these are unauthenticated (see v1-cache-no-auth), an attacker can issue many concurrent force_refresh requests to burn LLM credits, saturate the shared GitHub token pool (causing 429/secondary-rate-limit failures for legitimate traffic), and tie up worker processes (only WORKERS=2 by default).
- **repro/trigger:** for i in $(seq 1 50); do curl 'http://host:1234/v1/repository/llm/json/github.com/o/r?force_refresh=true' & done -> 50 concurrent paid LLM pipelines, no throttle.
- **fix:** Require verify_token (removes anonymous abuse) AND add request rate limiting / concurrency caps on the extraction routes; consider rejecting force_refresh from untrusted callers or bounding it.
- **verifier:** CONFIRMED REAL. Verified against actual code.

1) No inbound rate limiting: grep for slowapi|Limiter|RateLimit|throttle across src/api.py and src/v2/api.py returns only OUTBOUND GitHub/provider rate-limit handling (X-RateLimit response headers, per-provider client RateLimiter for ORCID/Zenodo). There is no per-client/inbound throttle or concurrency cap on any extraction route. The only middleware (api.py:369 add_request_context) is request-ID logging.

2) v1 extraction routes are caller-unauthenticated. The 5 v1 routes (api.py:784 get_org_json, 901 get_user_json, 1031, 1198, 1425 llm_json) depend ONLY on Depends(validate_github_token). That dependency (src/v1/utils/github_dependency.py:17) reads the SERVER's own GME_GITHUB_TOKEN env var and calls GitHub's /rate_limit to confirm the deployment is configured — it takes NO caller credential and rejects nothing from anonymous clients. Decisively, the codebase HAS a real caller-auth mechanism: src/v2/auth.py:verify_token (HTTPBearer against API_TOKEN, fails closed, hmac.compare_digest), and it guards every v2 route (dozens of Depends(verify_token) in src/v2/api.py). But verify_token appears 0 times in src/api.py and there is no router-level dependencies= on the v1 routes (they hang off the root app). So v1 is genuinely open while v2 is protected — confirming the v1-cache-no-auth precondition this finding relies on.

3) Heavyweight paid pipeline + force_refresh bypass confirmed. llm_json (api.py:1488-1495) constructs Repository(full_path, force_refresh=force_refresh) and calls run_analysis(run_gimie=True, run_llm=True, run_user_enrichment, run_organization_enrichment). In src/v1/analysis/repositories.py:2841, `if not self.force_refresh and self.check_in_cache(...)` — force_refresh=true skips the cache check entirely and runs PydanticAI Agents (src/v1/agents/agents_management.py:90, retries=3) against real LLM providers, plus GIMIE/GitHub/web/Infoscience lookups. So force_refresh=true reliably forces fresh paid LLM work per request.

4) Public exposure + low worker count confirmed by the compose file added on this branch (tools/deploy/docker-compose.yml): ports "${APP_PORT:-1234}:1234" publishes the API directly to the host with no auth gateway in the stack, and WORKERS: ${WORKERS:-2} confirms the default 2 workers. GME_GITHUB_TOKEN is a shared (rotating) token pool, so concurrent force_refresh calls amplify into the shared GitHub quota and LLM budget while tying up the 2 workers.

The claimed repro (50 concurrent unauthenticated force_refresh=true requests -> 50 paid pipelines, no throttle) is accurate. Severity high is correct: unauthenticated + publicly exposed + paid-LLM and shared-GitHub-token amplification + cache-bypassable + only 2 workers. Nuance for the fix: the dominant root cause is the missing caller auth on v1 (verify_token already exists and simply was not wired onto v1, presumably an oversight when v2 was hardened); the proposed verify_token requirement alone removes the anonymous-abuse vector, and rate limiting/concurrency caps are sound defense-in-depth on top. Not a framework guarantee or misread — the gap is real and exploitable.

### /query ad-hoc SQL has no row/time/memory limits — trivial DoS
- **id:** `query-adhoc-resource-dos` · **kind:** vulnerability · **confidence:** high · **group:** standalone-index-apps
- **endpoint:** POST /query (sql=...) on all 6 apps
- **location:** `src/index/github_repos/retrieval/sql.py:89`
- **what:** _execute runs the validated SQL with no LIMIT injection, no statement timeout, no memory cap, and then materializes the entire result via cur.fetchall() into a list of dicts (_row_to_dict). An attacker can submit `SELECT * FROM works, works b, works c` (cross join) or a recursive CTE (`WITH RECURSIVE r(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM r) SELECT * FROM r` — starts with WITH, no forbidden keyword) to exhaust CPU/RAM and OOM-kill the worker. fetchall() also buffers arbitrarily large result sets in memory. There is no pagination cap. This compounds with the no-auth finding.
- **repro/trigger:** POST /query {"sql":"WITH RECURSIVE r(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM r) SELECT n FROM r"} -> unbounded memory/CPU growth, worker hang/OOM.
- **fix:** On the ad-hoc connection set a hard statement timeout and memory limit (DuckDB: SET statement_timeout / SET memory_limit / SET max_memory on the read-only connection), enforce a server-side LIMIT, and stream/cap result rows instead of fetchall(). Reject recursive CTEs or cap recursion. Require auth.
- **verifier:** CONFIRMED against the code. The finding is accurate on every load-bearing claim.

1) Attacker-controlled SQL reaches the engine. /workspaces/project/src/index/github_repos/api.py:77-91 exposes POST /query; when req.sql is set it calls run_adhoc(req.sql, req.params) (line 88). run_adhoc (sql.py:106-113) only calls _validate_adhoc then _execute. _validate_adhoc (sql.py:27-34) only checks the statement starts with SELECT/WITH and contains none of 14 forbidden keywords. None of the keywords are LIMIT/timeout/memory related, so arbitrary read queries pass.

2) No row/time/memory limits, full materialization. _execute (sql.py:89-103) runs store.connect().execute(sql, ...) and returns _row_to_dict(cur), which does cur.fetchall() into a list of dicts (sql.py:84-86). No LIMIT injection, no SET statement_timeout, no SET memory_limit/max_memory, no streaming, no pagination cap. I grepped the whole src/ tree: there is zero DuckDB resource-limit configuration anywhere (the only SET hits are ON CONFLICT DO UPDATE SET upserts). Notably, github_repos _execute uses store.connect() = duckdb.connect(path) (duckdb_store.py:47-51), a read-WRITE handle — not even the read_only() context manager, contradicting the module docstring.

3) The repro payloads actually pass validation. I executed the exact validator logic: the recursive CTE `WITH RECURSIVE r(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM r) SELECT n FROM r` -> ACCEPTED (starts with WITH, no forbidden keyword), the cross join `SELECT * FROM works, works b, works c` -> ACCEPTED, and `SELECT * FROM generate_series(1, 100000000000)` -> ACCEPTED. The unbounded recursive CTE never terminates (CPU/hang and unbounded growth toward DuckDB's default ~80%-RAM memory_limit, spilling to a temp dir and filling disk); the cross join produces O(n^3) rows that fetchall() buffers into Python dicts, a guaranteed worker OOM independent of any DuckDB limit.

4) No auth, network-exposed, all 6 apps. The /query endpoint has no Depends/auth dependency, no API key, no middleware. grep across all six api.py files (github_repos, openalex, orcid, renkulab, swissubase, zenodo_records) found no Depends/api_key/Authorization/HTTPBearer/add_middleware. API_TOKEN (mentioned in deploy compose) is not wired into any index app. All six expose POST /query + run_adhoc and all six retrieval/sql.py materialize via fetchall(). This genuinely compounds with the no-auth finding as stated.

Severity: high is appropriate. A single unauthenticated request hangs/OOM-kills the worker; it is trivially reproducible and affects all six standalone index apps. Not raising to critical because impact is availability/DoS of a query worker (no data exfiltration or RCE beyond what the separate no-auth/read-write-connection findings cover), but high is correct.

### All /v1/* routes are unauthenticated despite docs claiming API_TOKEN guards them
- **id:** `v1-routes-unauthenticated` · **kind:** vulnerability · **confidence:** high · **group:** cross-cutting
- **endpoint:** /v1/* (all)
- **location:** `src/api.py:784`
- **what:** None of the v1 routes wire in src/v2/auth.py verify_token. The repository/user/org routes only declare Depends(validate_github_token) (src/api.py:802,923,1093,1279,1450), which validates the SERVER's own GME_GITHUB_TOKEN against api.github.com/rate_limit — it never inspects a client Authorization header. The cache-management routes (/v1/cache/*) have NO dependency at all. Yet docs/v2-api-reference.md:26 states "/v1/* routes share the same API_TOKEN and behave the same way" and line 315 lists API_TOKEN as "Bearer token guarding /v1/* and protected /v2/* routes." So the documented auth contract is not enforced: any unauthenticated client that can reach the port can trigger the full v1 LLM+GIMIE enrichment pipelines (expensive, burns the server's LLM credits and GitHub quota) and read cache contents.
- **repro/trigger:** With API_TOKEN set on the server, `curl http://host:1234/v1/cache/stats` and `curl http://host:1234/v1/repository/gimie/json-ld/https://github.com/sdsc-ordes/gimie` both succeed with no Authorization header (only require the server to have GME_GITHUB_TOKEN for the latter).
- **fix:** Add `_token: Annotated[str, Depends(verify_token)]` to every v1 route handler in src/api.py (or attach `dependencies=[Depends(verify_token)]` on app.include of the v1 routes / a sub-router). Keep validate_github_token as a separate concern. Add a regression test asserting 401 without a bearer token on a representative v1 route.

- **org_name/username taken from last path segment is interpolated unescaped into api.github.com URLs** (`org-user-path-segment-github-api-traversal`, src/api.py) — The finding's core exploitability claim is wrong because of how Starlette/FastAPI and the split-on-slash extraction interact.

Code path: src/api.py:847-848 and :977-978 do `_assert_github_host(full_path)` then `org_name = full_path.split("/")[-1]` / `username = full_path.split("/")[-1]`. These are passed to Organization(...)/User(...) which reach the parsers that f-string them into URLs (orgs_parser.py:124,229,244,256,274; users_parser.py:170 etc.). The base host is hardcoded `self.rest_base_url = "https://api.github.com"` (orgs_parser.py:24).

The claimed repro `/v1/org/llm/json/github.com/..%2f..%2frate_limit` does NOT work. I reproduced the route with FastAPI's TestClient: the `{full_path:path}` converter URL-decodes %2f -> / BEFORE the handler runs, so full_path arrives as `github.com/../../rate_limit`. Then `full_path.split("/")[-1]` returns `rate_limit` — a clean segment with no slashes, no dots, no encoded separators. Double-encoding (`%252f`) decodes once to `/`, again splitting into separate segments, so `[-1]` is still a plain token. There is therefore no way to smuggle `/` or `%2f` into org_name/username, so the requests-built URL cannot be redirected to a different api.github.com endpoint via slash injection (verified: requests normalizes `/orgs/../../rate_limit` only when the dots literally appear, which they don't here).

The only characters that can survive into org_name are literal dots: `github.com/%2e%2e` yields org_name = `..`, producing `https://api.github.com/orgs/..` which urllib3 normalizes to the API root `https://api.github.com/` (benign, less-specific endpoint), not the attacker-chosen `rate_limit`/`meta`. That is not meaningful request-path tampering and cannot reach an arbitrary endpoint as the repro asserts.

Additionally, both endpoints are auth-gated via `Depends(validate_github_token)` (github_dependency.py:17), the host is fixed to api.github.com, the GraphQL path is parameterized (login: $org_name), and the token only ever goes to GitHub. So even the bounded scenario requires a valid token and yields no security-relevant outcome.

The finding correctly notes the values are f-stringed unescaped (reasonable hardening to add quote()+charset validation), but the described attack — encoded-traversal segment reaching the URL and redirecting requests — is not achievable. Marking real=false; severity was already 'low', but the concrete exploit it rests on does not exist.
- **_assert_github_host validates only the parsed host but the full raw full_path is appended to the gimie sidecar URL** (`gimie-host-check-only-checks-parsed-host`, src/api.py) — The finding's factual observations are accurate but the claimed repro is not exploitable, and there is a second validation layer that blocks it.

Confirmed facts:
- src/api.py:84-113 `_assert_github_host` only checks `urlparse(candidate).hostname in {github.com, www.github.com}`; it never validates the path/query/fragment, and only prepends `https://` when `://` is absent (so `http://github.com/...` passes). Correct.
- The same raw `full_path` flows to the sidecar: route `gimie` (api.py:1115-1119) -> `Repository(full_path).run_analysis(run_gimie=True)` -> `run_gimie_analysis` (repositories.py:85) -> `extract_gimie(self.full_path)` (gimie_methods.py:238/260) -> `extract_gimie_via_api(full_path)` which builds `url = f"{base}/gimie/{kind}/{full_path}"` (gimie_api_client.py:66). Correct.

Why it is NOT a real/exploitable issue:
1) Second stricter gate blocks the claimed trigger. `Repository.__init__` (repositories.py:54) calls `is_github_repo_public(full_path)`, which uses an anchored regex `https?://github\.com/([^/]+)/([^/]+?)(?:\.git)?/?$` (utils/utils.py:32-35). The trigger `https://github.com/o/r?x=../../internal` does NOT match (the `?x=...` breaks the `$` anchor), so `self.is_public = False`. `run_analysis` then returns early at the `if not self.is_public` gate (repositories.py:2829-2834) BEFORE `run_gimie_analysis`/`extract_gimie_via_api` is ever called. So the malformed `full_path` never reaches the sidecar URL on the cited endpoint. The host check is weak in isolation, but the owner/repo regex effectively canonicalizes shape downstream.
2) No SSRF/traversal primitive even if it reached the client. The injected content is appended as path/query onto a fixed internal trusted `base` (e.g. `http://gme-gimie-api:15400`). A query string like `?x=../../internal` cannot change the request authority/host or perform HTTP-layer path traversal; `requests.get` targets the fixed internal host regardless. The finding itself concedes the blast radius is limited.
3) The endpoint is auth-gated (`Depends(validate_github_token)`, api.py:1093), so it is not an unauthenticated surface.
4) The `http://` scheme-downgrade sub-claim is inert: `full_path`'s scheme is never used to open a connection; it is only a path segment appended to the sidecar `base`, so no actual connection is downgraded.

This is at most a cosmetic divergence between validated value and used value (defense-in-depth nicety), already correctly rated low/hardening by the finder and acknowledged as limited blast radius. Since it is not exploitable or incorrect in the actual code (the `is_public` regex gate prevents the repro, and the appended query cannot redirect the request), real=false. Adjusting severity to info given the issue is fully defended in practice.
- **Raw exception text echoed in HTTP responses (info disclosure)** (`error-detail-str-exc-disclosure`, src/v2/api.py) — The cited code lines are all accurate: the v2 pipeline handler does return V2ErrorResponse(detail=str(exc)) at src/v2/api.py:900-908 (500) and 889-897 (502); compact returns detail=f"compact failed: {exc}" (4152); stats returns detail=f"stats query failed: {exc}" (4201); v1 gimie echoes upstream ConnectionError text (src/api.py:1184/1188) and f"GIMIE extraction failed: {e!s}" (1194); the global ValueError handler returns {"message": str(exc)} (1716). However, the finding overstates exploitability and severity for two concrete reasons grounded in the code:

1) Every cited endpoint is authenticated. All v2 routes (extract at src/v2/api.py:774, compact at 4104, stats at 4166) depend on verify_token (src/v2/auth.py), a fail-closed HMAC bearer check against API_TOKEN. The v1 gimie route depends on validate_github_token (src/api.py:1093) and additionally validates host via _assert_github_host (1115). 2) The most alarming claim — "potentially including tokens embedded in failing request URLs" — is not supported by the code. GitHub auth is header-based (Authorization: token <t> in src/v1/utils/github_dependency.py:62-63), and the gimie sidecar reads its token from the ACCESS_TOKEN env var (tools/deploy/docker-compose.yml:55). Additionally, the SQL/paths surfaced are not attacker-controlled into a query (compact/stats run fixed COUNT/EXPORT operations on server-configured providers), and logger.exception is already called server-side in every cited path (888, 899, 4149, 4198, 1191).

What remains is a genuine but minor hardening nicety: str(exc) can expose internal paths, DuckDB fragments, or library internals to an authenticated operator/consumer, and replacing it with an opaque detail + run_id (already generated at src/v2/api.py:808) would be cleaner. - **Server GitHub token could surface in upstream error strings echoed to clients** (`github-token-leak-via-upstream-error`, src/api.py) — Verified against actual code; the specific claim (GitHub token surfacing in upstream error strings echoed to clients) is not present or exploitable.

EVIDENCE:
1. Token transport is header-only, never URL-embedded. The GIMIE GitHub extractor sets auth as {"Authorization": f"token {self.token}"} (gimie/extractors/github.py:264) and validate_github_token uses f"token {token}" as an Authorization header (src/v1/utils/github_dependency.py:63). grep for URL-embedded credentials (token@, ://...:...@, ?token=, access_token=, x-access-token) across /workspaces/project/src/ returns ZERO hits.

2. The GIMIE ConnectionError that reaches src/api.py:1172-1189 is constructed in gimie/extractors/github.py:273 as f"Failed to connect to GitHub API: {str(e)}" where e is a requests.exceptions.RequestException. I empirically tested what str() of a requests RequestException contains when a request is made with an Authorization header: the message is HTTPConnectionPool(host='...', port=...): Max retries exceeded with url: /user (...) — it contains host/port/URL-path only, and the Authorization header value is ABSENT (HAS_TOKEN check returned False). requests/urllib3 exceptions do not serialize request headers into their str().

3. Therefore msg = str(e) at src/api.py:1174 cannot contain the token, and returning detail=msg (lines 1184/1188) and logging it (line 1176) cannot leak credentials given the current header-based clients. The same applies to validate_github_token's logger.error(f"...: {e}") at github_dependency.py:121 — e is a header-auth RequestException.

4. The finding text itself concedes current clients use Authorization headers, not URL tokens, and frames the leak as conditional on a hypothetical future client that embeds the token in a URL/header landing in exception text — which does not exist in the code. That is speculative defense-in-depth, not a present vulnerability.

NOTE: The over-broad practice of returning raw upstream str(e) as the HTTP detail (and the 502 path at line 1194 doing f"GIMIE extraction failed: {e!s}") is a legitimate but SEPARATE concern, which the finding explicitly defers to the error-detail finding. Severity already 'low'; downgrading to 'info' since it is non-exploitable as described.
